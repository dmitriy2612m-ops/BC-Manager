## Реализация Java (Сессия 5)

| Компонент | Назначение |
| :--- | :--- |
| `LeasePricingService` | Алгоритм 3 через полиморфный `RentCalculable`, скидки, НДС, график платежей |
| `SpaceMatchingService` | Алгоритмы 1 и 2: проверка конфликтов, фильтрация, Score и ранжирование |
| `BillingService` | Алгоритм 4: пени, агрегат долга по договорам, фиксация оплат |
| `MaintenanceQueueService` | Алгоритм 5 на `PriorityQueue` + `Prioritizable` |
| `AnalyticsService` | Алгоритм 6 через `HashMap`/`TreeMap`, CSV через `Exportable` |
| `PremisesService`, `TenantService`, `ContractService` | CRUD, предпросмотр и оформление договора, синхронизация статусов |

Порядок округления в Java повторяет Python: `net` → НДС от округлённого `net` → `total = net + НДС`,
что даёт побайтовое совпадение денежных строк (`HALF_UP`, 2 знака).

Состав синтетических наборов: 1000/10000 помещений, 500/5000 договоров и платежей,
10/100 заявок. Рост времени почти линейный, что подтверждает заявленные в спецификации
сложности O(N), O(P), O(Q log Q).

## Замечания по эталону

В Сессии 2 обнаружены и исправлены ошибки базовой версии `expected_results.json` (Сессия 1
помечала ряд значений как предварительные):

1. **Алгоритм 3, офис с мебелью (12 мес):** арифметическая опечатка в `net_monthly`
   (`57287.50` вместо верного `57307.50`); скорректирован весь набор (`vat`, `total`, график).
2. **Алгоритм 2:** ожидались помещения в статусах `RENTED`/`RESERVED` и без учёта
   скидки/НДС в `estimated_monthly_cost`; кроме того, офисный сценарий `office_85_sqm`
   фактически не имеет подходящих помещений (DRAFT-конфликт + фильтр площади), что теперь
   зафиксировано как ожидаемый пустой результат.
3. **Алгоритм 4, агрегат:** по контракту 1 есть два просроченных платежа (не один), и по
   спецификации в агрегат входят все договоры, включая нулевые строки.
4. **Алгоритм 5:** `HIGH`, ожидающая 50 часов, по правилу эскалации поднимается до веса 1 —
   очередь переупорядочена.
5. **Алгоритм 6:** суммарная площадь 15 помещений равна `746.40` (не `754.40`); на 3-м этаже
   нет действующего договора (договор 5 — `COMPLETED`); ближайший к истечению договор истекает
   через 44 дня, поэтому окно «30 дней» пусто.

> Эталон теперь актуален (`revised_in_session: 2`) и служит базой для parity-теста Сессии 5.
